# Architecture

One Next.js application serves both the public website and the Payload admin
panel. There is no separate backend service.

> `vite.config.js`, `index.html`, `src/main.jsx` and most of `src/components/`
> are leftovers from the pre-Next build. The live application is `app/`. The
> one file under `src/` that is still live is `src/index.css`, imported by the
> website layout.

## Frontend

**Framework:** Next.js 16 (App Router), React 19, Tailwind CSS v4 (via
`@tailwindcss/postcss`), `lucide-react` for icons.

### `app/` structure

```
app/
  (website)/            Public site — has its own layout, Navbar/Footer
    layout.jsx          Metadata, JSON-LD, next/font, imports src/index.css
    page.jsx            Homepage
    about/ contact/ privacy-policy/ terms/
    properties/         (listing)/page+loading.jsx, [slug]/ detail
    projects/           (listing)/page+loading.jsx, [slug]/ detail
    [...notFound]/      Claims unmatched URLs so they get the branded 404
    error.jsx  not-found.jsx
  (payload)/            Payload admin + its REST/GraphQL API
    admin/[[...segments]]/   Admin panel
    api/[...slug]/route.ts   Payload API
    custom.scss              Admin theming (RER palette)
  api/contact/route.ts  Public contact form endpoint
  robots.ts  sitemap.ts  manifest.ts
  icon.png  apple-icon.png   Favicon / home-screen icon (file conventions)
```

`components/` holds the public components, grouped by area: `home/`,
`properties/`, `projects/`, `layouts/`, `contact/`, `ui/`, plus
`components/payload/` for custom admin UI (status badge, price cell,
brochure-convert view, list-table scroll sync, agreement countdown, slug update)
and `components/payload/dashboard/` for the admin console that replaces
`/admin`.

### Server / client conventions

Server components are the default; every route file is a server component and
most section components are too. `"use client"` is the exception, used only
where interaction genuinely requires it:

`EnquiryPopup`, `contact/ContactForm`, `home/FeaturedShowcase`,
`home/HeroPropertySearch`, `layouts/Navbar`, `layouts/FooterAccordion`,
`layouts/FooterCtaGate`, `properties/PropertyFilterBar`,
`properties/PropertyGallery`, `ui/CardSlider`, `app/(website)/error.jsx`, and
the `components/payload/*` admin components.

Data is always fetched in the server component (usually the route file) and
passed down as props. Client components never call the Payload API themselves.

### Homepage components

`app/(website)/page.jsx` fetches in one `Promise.all` and renders, in order:

| Component | Data |
| --- | --- |
| `home/Hero` | `getPropertyLocalities()` + `getHomeBanners().hero` |
| `FloatingWhatsapp` | static contact config |
| `home/Services` | static (the four business intents) |
| `home/FeaturedShowcase` | `getFeaturedProperties({ limit: 3 })` + `getProjects({ isNew: true, limit: 3 })` |
| `home/AboutTeaser` | static copy — "A legacy built on trust"; photograph from `getHomeBanners().ourStory` |
| `home/OfficialChannelPartners` | `getChannelPartners()` |

### Styling

`src/index.css` holds the Tailwind import, the `@theme` brand tokens
(`--color-rer-navy`, `--color-rer-gold`, `--color-rer-gold-text`,
`--color-rer-sand`, `--font-cormorant`, ...), a
zero-specificity focus-visible treatment, the `user-select: none` rule for real
controls (`button, summary, [role="button"]`), and the channel-partner marquee
keyframes. Components still use raw hex (`#081221`, `#B8862F`) in many places;
the tokens are the canonical values and migrating onto them is mechanical, not
urgent.

## CMS

**Payload 3** with the Postgres adapter (`@payloadcms/db-postgres`) and the
Lexical rich-text editor.

- **Config:** `payload.config.ts` (aliased as `@payload-config` in
  `tsconfig.json`). It registers collections, the S3 storage plugin, two
  brochure-convert endpoints, custom admin components, and an `onInit` that
  ensures the property/project ID sequences exist and seeds default amenities.
- **Collections** (`collections/`): `Users`, `Properties`, `Projects`,
  `Amenities`, `ChannelPartners`, `Media`, `ContactInquiries`,
  `WebsiteBanners`. See
  `DATA-MODEL.md`.
- **Supporting code:** `collections/hooks/` (ID assignment and sequence
  allocation/schema declaration — `idSequenceSchema.ts` keeps the dev push from
  dropping the ID sequences — media-folder
  assignment, default amenities, ID-sequence sync) and `collections/endpoints/`
  (brochure convert validate/create, generate nearby locations).
- **Types:** `payload-types.ts` at the repo root, generated by
  `npx payload generate:types`. Regenerate it after any collection change.

### The admin console (`/admin`)

The admin landing page is the **RER Property Management Console**, registered
as `admin.components.views.dashboard` in `payload.config.ts`. That option
replaces only the *body* of `/admin` — Payload's own `DashboardView` still
wraps it (`HydrateAuthProvider`, `SetStepNav`), and the nav rail, account
menu and every collection route are untouched. It does replace Payload's
collection-cards widget, so the console ends with its own permission-filtered
collection grid.

- **UI:** `components/payload/dashboard/` — server components, no client
  JavaScript of their own (the only client boundary is Payload's `Gutter`).
  `RerConsoleView` is the registered entry point; the rest are sections.
- **Data:** `lib/admin-console/` (below). The console reads the same Postgres
  data through the Local API as everything else. No second database, no
  cached snapshot, no activity log.
- **Styling:** `app/(payload)/custom.scss` §11, built entirely from the `--rer-*`
  tokens in §1 and the panel recipe in §3.
- Status and agreement-countdown badges take their tiers and colours from
  `lib/statusTiers.ts` and `lib/properties/agreementCountdown.ts`, shared with
  the list-view Cells so the same value cannot render two different ways.

### The property slug field

`slug` on Properties is generated once, on create, by
`collections/hooks/assignPropertySlug.ts` (see `DECISIONS.md`). The admin adds
one control to it: a **Slug Update** button that rebuilds the value from the
form's current BHK, property type, locality and RER ID.

- `components/payload/RegenerateSlugButton.tsx` — client component, registered
  as the field's `admin.components.afterInput`, so Payload renders it inside the
  field's own wrapper right after the input. It calls the same
  `buildPropertySlug()` the create hook uses, writes to form state only
  (`dispatchFields` + `setModified`), and is disabled until the property has
  been saved and has a `propertyId`.
- `app/(payload)/custom.scss` §12 turns that field's `.field-type__wrap` into a
  two-column grid so the button sits beside the input rather than under it, and
  stacks them again below 880px.
- It is needed most often after **duplicating** a property: the duplicate gets a
  fresh RER ID but inherits the source listing's descriptive tokens, so its slug
  describes the wrong unit until the button is pressed.

### How CMS data reaches the website

Server component -> `lib/<area>/get*.ts` -> `getPayloadClient()` (Payload
**Local API**, `lib/payload.ts`) -> `map*.ts` -> plain `Public*` object ->
props.

The public site never calls the Payload REST API over HTTP. Every public query
passes `overrideAccess: false`, so collection access control is enforced on top
of the explicit `where` clause.

## Media

One `media` collection backs every image on the site.

- **Storage:** Supabase Storage over its S3-compatible endpoint
  (`@payloadcms/storage-s3`, configured in `payload.config.ts`). No ACL and no
  `disablePayloadAccessControl`, so files stream through this app's own
  `/api/media/file/:filename` route; the bucket is never hit directly by the
  browser. Object keys are flat filenames — no prefix.
- **Folders:** `folders: true` on the Media collection. Properties and Projects
  each own one folder named after their RER ID, assigned by
  `collections/hooks/assignMediaFolder.ts`.
- **Derivatives** (`collections/Media.ts`, `imageSizes`), all cut from the
  original upload, all `fit: 'inside'` + `withoutEnlargement`:
  `thumbnail` 400px WebP q80 (admin grid), `card` 800px WebP q82 (not currently
  read by the site), `large` 4096px WebP q90 — **the one the public site serves**.
- **`toDeliveryImage()`** (`lib/mediaUrl.ts`) is the single entry point. It
  returns the `large` derivative when that derivative is WebP and wide enough,
  otherwise falls back to the original, and returns `{ url, width, height }`
  together because callers also use the dimensions for Open Graph.
  `toRelativeMediaUrl()` strips `SITE_URL` so `next/image` fetches from this app
  instead of making a self-referential external request.
- **`next/image`** config lives in `next.config.mjs`: the site's own origin is
  allow-listed under `/api/media/**`; `formats` is **WebP only** (AVIF is
  deliberately excluded — Next rescales `quality` before the AVIF encoder);
  `qualities` is an explicit allow-list of `[75, 82, 85, 88]` and Next 16
  returns HTTP 400 for anything outside it; `minimumCacheTTL` is 7 days.
  Conventions in use: 82 for cards and listing tiles, 85 for detail heroes and
  plans, 88 for full-bleed/lightbox and partner logos.
- **Card `sizes`** come from `lib/cardImageSizes.ts` and are a **required prop**
  on `PropertyCard`/`ProjectCard` — `LISTING_CARD_SIZES` for the two-up
  `/properties` grid, `SHOWCASE_CARD_SIZES` for the one-up sliders and the
  projects listing, and `showcaseCardSizes(count)` for the narrowed
  FeaturedShowcase tracks. Each clause is the card's real rendered width at that
  breakpoint; above 1280px every grid is capped by `max-w-7xl`, so the clause is
  a fixed `384px` rather than a `vw` unit. Card image boxes are `aspect-[3/2]`,
  matching the dominant source aspect so `object-cover` crops almost nothing.
  See `DECISIONS.md`: these strings encode grid arithmetic and go stale
  silently if a card grid changes.
- **SVG:** Payload/sharp produces **no derivatives** for SVG uploads — the
  `sizes` entries come back null. Vector logos are therefore served as the
  original file with `unoptimized` on `next/image`; running them through the
  optimizer would rasterise them. Only the channel-partner path does this today
  (`lib/channel-partners/mapChannelPartner.ts` sets `isVector`).
- A plain `<img>` with a hand-written `srcSet` is used for the two
  Unsplash-hosted decorative photos (`home/Hero`, `home/AboutTeaser`), which are
  not Media records. Both are interim fallbacks, shown only while their banner
  placement has no published record (below).

### Page banners

Banner photography and copy are CMS content: the **`website-banners`**
collection (`collections/WebsiteBanners.ts`, admin group *Website*), with
images as upload relationships to `media`. Admin how-to:
`docs/BANNER-ASSETS.md`.

- **Placements** are a fixed list in `lib/website-banners/placements.ts`
  (`home`, `our-story`, `properties`, `rentals`, `commercial`, `projects`,
  `about`, `contact`), shared by the collection's select and the frontend.
  Each has a `kind` (`hero` / `page` / `image`) that drives which admin fields
  show, which are validated, and which the mapper keeps.
- **Data:** `lib/website-banners/` — `getWebsiteBanners(placements)` (one
  Local API query, `overrideAccess: false`, `draft: false`, published + enabled
  only, `-updatedAt`), `mapWebsiteBanner()` (refuses non-published/disabled
  docs, drops fields the placement does not use, re-checks CTA links with
  `safeBannerHref()`, images via `toDeliveryImage()`), and `resolveBanner()`
  (own record → for `rentals`/`commercial` the `properties` record →
  `BANNER_DEFAULTS`). `getBanner(placement)` and `getHomeBanners()` are what
  routes call. A failed read logs and degrades to the defaults.
- **Rendering:** route files fetch and pass a `ResolvedBanner` down.
  `components/ui/PageBanner.jsx` renders `/properties`, `/projects`, `/about`,
  `/contact`; its `BannerBackdrop` also serves `home/Hero` and
  `home/AboutTeaser` (Our Story). `/properties` picks its placement from the
  filters with `propertiesBannerPlacement()` (`commercial` > `rentals` >
  `properties`).
- **No record** (`source: 'default'`) renders exactly the pre-CMS design: the
  same copy, the navy header, and for the hero and Our Story the interim
  Unsplash `<img>`. A published record whose image is gone renders without a
  photograph — never the Unsplash one.
- Images: `next/image` `fill`, quality 85, `sizes="100vw"` (Our Story: its
  column sizes, lazy), `fetchPriority="high"` for the headers. With a mobile
  image, a `<picture>` via `getImageProps()`; otherwise one source re-framed per
  breakpoint through `--banner-pos` CSS variables. Overlay strength and
  alignment are fixed class recipes in the components — no CSS reaches the CMS.
- **Revalidation:** `collections/hooks/revalidateWebsiteBanner.ts` calls
  `revalidatePath()` for the placement's page when a published version changes.
- `scripts/seed-website-banners.ts` — create-only draft per placement.
  `scripts/prepare-banner.mjs` — sharp export of a master to
  `banner-exports/` for upload.

## Fonts, icons and social images

- **Cormorant Garamond** is self-hosted by `next/font/google` in the website
  layout, weight 600 only, publishing the family as `--font-cormorant-src`.
  `src/index.css`'s `@theme` maps that onto `--font-cormorant`, which is what
  makes the `font-cormorant` utility exist. A font utility with no `@theme` key
  emits nothing and fails silently — that is exactly what used to happen here.
  Everything else uses Tailwind's default `font-serif`/sans stacks; there is no
  other webfont and no request to any font CDN.
- **Icons** come from Next's file conventions: `app/icon.png` (48px tab icon)
  and `app/apple-icon.png` (180px). `app/manifest.ts` points at
  `public/icon-192.png` and `public/icon-512.png`. All four are the same navy
  house mark, generated with sharp from `public/logo-HOUSE-white.svg`.
  The manifest is deliberately `display: 'browser'` — this is not a PWA.
- **Social images.** `DEFAULT_OG_IMAGE` in `lib/seo/ogImage.ts` points at
  `public/og-default.png` (1200x630 brand lockup on navy) and must be listed
  explicitly by any page that declares its own `openGraph` object — Next
  replaces that object rather than merging into it. See `DECISIONS.md`.
  Property and project detail pages pass their own first photograph and fall
  back to this constant.

## Security and transport

- **`next.config.mjs` `headers()`** applies HSTS (production only),
  `X-Content-Type-Options: nosniff`, `Referrer-Policy:
  strict-origin-when-cross-origin` and `X-Frame-Options: SAMEORIGIN` to every
  route, and `poweredByHeader: false` removes the stack banner. SAMEORIGIN
  rather than DENY because Payload's admin frames its own routes.
  There is no application-level HTTP->HTTPS redirect; Railway handles that.
- **`POST /api/contact`** validates every field server-side, builds the record
  field-by-field (never a spread of the request body, so `status` and `notes`
  cannot be set by a client), and is defended by a honeypot, a minimum
  render-to-submit interval, and `lib/rateLimit.ts` — an in-process fixed
  window, 5 requests per 10 minutes per IP, answering 429 with `Retry-After`.
- **`components/Analytics.jsx`** renders nothing unless both
  `NEXT_PUBLIC_ANALYTICS_SRC` and `NEXT_PUBLIC_ANALYTICS_DOMAIN` are set, and
  refuses a non-https src. No provider is configured and no values are
  committed. It is shaped for a cookieless provider on purpose — the site
  currently needs no cookie banner and that is worth keeping.

## Data fetching

Every area follows the same shape under `lib/`:
`publicScope.ts` (which statuses are public) -> `get*.ts` (queries) ->
`map*.ts` (CMS doc to `Public*` type) -> `types.ts` -> `index.ts` (barrel).

### Properties — `lib/properties/`

- `publicScope.ts` — `PUBLIC_STATUSES = ['available', 'under-offer']`, plus
  `publicStatusWhere()`, `publicFeaturedWhere()` (status + `tags` contains
  `featured`), `publicSlugWhere(slug)` and the `isPublicStatus()` guard.
- `getProperties(options)` — listing query at `depth: 2`, limit 100. Handles
  purpose / category / locality / BHK / budget. Budget is applied to a
  purpose-specific price field (`pricing.price` for sale, `pricing.rentAmount`
  for rent, `pricing.monthlyLeasePayment` for lease), so a budget filter
  without a purpose is skipped rather than applied to the wrong column.
- `getPropertyLocalities(scope)` / `resolveLocalitySlug()` — filter options
  derived from live inventory, so the UI never offers an empty locality.
- `getFeaturedProperties({ limit })` — `publicFeaturedWhere()`, `-updatedAt`.
- `getPropertyBySlug(slug)` — wrapped in React `cache()` because the route uses
  it in both `generateMetadata` and the page body; returns `null` when the slug
  is not public.
- `getSimilarProperties()` — related inventory for the detail page.
- `mapProperty()` — the only place a CMS document becomes a `PublicProperty`.
  It converts Lexical rich text to HTML/plaintext, formats INR
  (`formatPrice.ts`), builds location display strings (`formatLocation.ts`),
  maps images through `toDeliveryImage()`, and refuses non-public documents.
- `filterParams.ts` — the URL query dialect: parse/serialize, budget bands,
  labels, and `legacyTypeToFilters()` for the old single `type` parameter.

### Projects — `lib/projects/`

Same shape. `PUBLIC_PROJECT_STATUSES` is `upcoming`, `under-construction`,
`ready-to-move`, `completed`, `sold-out` — everything except `draft`.
`getProjects({ projectType, status, isNew, limit })` at `depth: 2`,
`getProjectBySlug()`, `getRelatedProjects()`, `mapProject()`.
Nearby-connectivity category labels come from `lib/nearby-locations/`.

### Channel partners — `lib/channel-partners/`

Deliberately the smallest version of the same pattern, with no `publicScope.ts`
because visibility is a single boolean:

- `getChannelPartners()` — `where: { active: { equals: true } }`, `depth: 1`
  (enough to populate the `logo` upload), limit 50,
  `sort: ['displayOrder', 'name']`.
- `mapChannelPartner()` — drops records with no name or an unpopulated logo,
  builds alt text from the partner name, re-validates that `websiteUrl` is
  http(s) before it can reach an `href`, and routes the logo through
  `toDeliveryImage()` unless it is an SVG.

### Website banners — `lib/website-banners/`

See *Page banners* above. Visibility is `_status: published` and
`enabled: true`, applied in the query, in the collection's public read access
and again in `mapWebsiteBanner()`.

### Admin console — `lib/admin-console/`

The only `lib/` area that is **not** part of the public-site pipeline: it has
no `publicScope.ts` and no `map*.ts`, because nothing it produces is ever
rendered outside the authenticated admin panel. Every query runs with
`overrideAccess: false` and the signed-in `user`, so field-level gates
(`ownerDetails`, `rentHistory`, `currentAgreementEndDate`) apply normally.

- `types.ts` — the shapes the console's sections render.
- `adminUrls.ts` — `stringifyWhere()` serializes a Payload `Where` into the
  bracket-notation query string the admin list view parses back
  (`where[status][equals]=rented`), plus the list/create/document URL
  builders. Every builder takes the admin route prefix as an argument; the
  console reads the real value from `config.routes.admin` rather than
  hardcoding `/admin`.
- `selectOptions.ts` — reads a select field's own `options` out of the
  sanitized config, so the console's status tiles are *generated from the
  schema* rather than from a list kept alongside it.
- `checks.ts` — the Needs Attention checklist. One `Where` per check.
- `loadConsoleData.ts` — runs every count and query in a single `Promise.all`
  and assembles `ConsoleData`.

The rule that holds the whole area together: **every number on the console is
a `payload.count()` over a `Where`, and that same `Where` is what the number's
link navigates to.** A tile and the list it opens are the same query, so they
cannot disagree. See `DECISIONS.md`.
