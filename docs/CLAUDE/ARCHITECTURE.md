# Architecture

One Next.js application serves both the public website and the Payload admin
panel. There is no separate backend service.

> `vite.config.js`, `index.html`, `src/main.jsx` and most of `src/components/`
> are leftovers from the pre-Next build. The live application is `app/`. The
> one file under `src/` that is still live is `src/index.css`, imported by the
> website layout.

## Frontend

**Framework:** Next.js 16 (App Router), React 19, Tailwind CSS v4 (via
`@tailwindcss/postcss`), `lucide-react` for icons.

### `app/` structure

```
app/
  (website)/            Public site — has its own layout, Navbar/Footer
    layout.jsx          Metadata, JSON-LD, imports src/index.css
    page.jsx            Homepage
    about/ contact/ privacy-policy/ terms/
    properties/         Listing + [slug] detail (+ loading.jsx)
    projects/           Listing + [slug] detail (+ loading.jsx)
    error.jsx  not-found.jsx
  (payload)/            Payload admin + its REST/GraphQL API
    admin/[[...segments]]/   Admin panel
    api/[...slug]/route.ts   Payload API
    custom.scss              Admin theming (RER palette)
  api/contact/route.ts  Public contact form endpoint
  robots.ts  sitemap.ts
```

`components/` holds the public components, grouped by area: `home/`,
`properties/`, `projects/`, `layouts/`, `contact/`, `ui/`, plus
`components/payload/` for custom admin UI (dashboard summary, status badge,
price cell, brochure-convert view).

### Server / client conventions

Server components are the default; every route file is a server component and
most section components are too. `"use client"` is the exception, used only
where interaction genuinely requires it:

`EnquiryPopup`, `contact/ContactForm`, `home/FeaturedShowcase`,
`home/HeroPropertySearch`, `layouts/Navbar`, `layouts/FooterAccordion`,
`layouts/FooterCtaGate`, `properties/PropertyFilterBar`,
`properties/PropertyGallery`, `ui/CardSlider`, `app/(website)/error.jsx`, and
the `components/payload/*` admin components.

Data is always fetched in the server component (usually the route file) and
passed down as props. Client components never call the Payload API themselves.

### Homepage components

`app/(website)/page.jsx` fetches in one `Promise.all` and renders, in order:

| Component | Data |
| --- | --- |
| `home/Hero` | `getPropertyLocalities()` |
| `FloatingWhatsapp` | static contact config |
| `home/Services` | static (the four business intents) |
| `home/FeaturedShowcase` | `getFeaturedProperties({ limit: 3 })` + `getProjects({ isNew: true, limit: 3 })` |
| `home/AboutTeaser` | static — "A legacy built on trust", i.e. the legacy section |
| `home/OfficialChannelPartners` | `getChannelPartners()` |

### Styling

`src/index.css` holds the Tailwind import, the `@theme` brand tokens
(`--color-rer-navy`, `--color-rer-gold`, `--color-rer-sand`, ...), a
zero-specificity focus-visible treatment, the `user-select: none` rule for real
controls (`button, summary, [role="button"]`), and the channel-partner marquee
keyframes. Components still use raw hex (`#081221`, `#B8862F`) in many places;
the tokens are the canonical values and migrating onto them is mechanical, not
urgent.

## CMS

**Payload 3** with the Postgres adapter (`@payloadcms/db-postgres`) and the
Lexical rich-text editor.

- **Config:** `payload.config.ts` (aliased as `@payload-config` in
  `tsconfig.json`). It registers collections, the S3 storage plugin, two
  brochure-convert endpoints, custom admin components, and an `onInit` that
  ensures the property/project ID sequences exist and seeds default amenities.
- **Collections** (`collections/`): `Users`, `Properties`, `Projects`,
  `Amenities`, `ChannelPartners`, `Media`, `ContactInquiries`. See
  `DATA-MODEL.md`.
- **Supporting code:** `collections/hooks/` (ID assignment, media-folder
  assignment, default amenities, ID-sequence sync) and `collections/endpoints/`
  (brochure convert validate/create, generate nearby locations).
- **Types:** `payload-types.ts` at the repo root, generated by
  `npx payload generate:types`. Regenerate it after any collection change.

### How CMS data reaches the website

Server component -> `lib/<area>/get*.ts` -> `getPayloadClient()` (Payload
**Local API**, `lib/payload.ts`) -> `map*.ts` -> plain `Public*` object ->
props.

The public site never calls the Payload REST API over HTTP. Every public query
passes `overrideAccess: false`, so collection access control is enforced on top
of the explicit `where` clause.

## Media

One `media` collection backs every image on the site.

- **Storage:** Supabase Storage over its S3-compatible endpoint
  (`@payloadcms/storage-s3`, configured in `payload.config.ts`). No ACL and no
  `disablePayloadAccessControl`, so files stream through this app's own
  `/api/media/file/:filename` route; the bucket is never hit directly by the
  browser. Object keys are flat filenames — no prefix.
- **Folders:** `folders: true` on the Media collection. Properties and Projects
  each own one folder named after their RER ID, assigned by
  `collections/hooks/assignMediaFolder.ts`.
- **Derivatives** (`collections/Media.ts`, `imageSizes`), all cut from the
  original upload, all `fit: 'inside'` + `withoutEnlargement`:
  `thumbnail` 400px WebP q80 (admin grid), `card` 800px WebP q82 (not currently
  read by the site), `large` 4096px WebP q90 — **the one the public site serves**.
- **`toDeliveryImage()`** (`lib/mediaUrl.ts`) is the single entry point. It
  returns the `large` derivative when that derivative is WebP and wide enough,
  otherwise falls back to the original, and returns `{ url, width, height }`
  together because callers also use the dimensions for Open Graph.
  `toRelativeMediaUrl()` strips `SITE_URL` so `next/image` fetches from this app
  instead of making a self-referential external request.
- **`next/image`** config lives in `next.config.mjs`: the site's own origin is
  allow-listed under `/api/media/**`; `formats` is **WebP only** (AVIF is
  deliberately excluded — Next rescales `quality` before the AVIF encoder);
  `qualities` is an explicit allow-list of `[75, 82, 85, 88]` and Next 16
  returns HTTP 400 for anything outside it; `minimumCacheTTL` is 7 days.
  Conventions in use: 82 for cards and listing tiles, 85 for detail heroes and
  plans, 88 for full-bleed/lightbox and partner logos.
- **SVG:** Payload/sharp produces **no derivatives** for SVG uploads — the
  `sizes` entries come back null. Vector logos are therefore served as the
  original file with `unoptimized` on `next/image`; running them through the
  optimizer would rasterise them. Only the channel-partner path does this today
  (`lib/channel-partners/mapChannelPartner.ts` sets `isVector`).
- A plain `<img>` with a hand-written `srcSet` is used for the two
  Unsplash-hosted decorative photos (`home/Hero`, `home/AboutTeaser`), which are
  not Media records.

## Data fetching

Every area follows the same shape under `lib/`:
`publicScope.ts` (which statuses are public) -> `get*.ts` (queries) ->
`map*.ts` (CMS doc to `Public*` type) -> `types.ts` -> `index.ts` (barrel).

### Properties — `lib/properties/`

- `publicScope.ts` — `PUBLIC_STATUSES = ['available', 'under-offer']`, plus
  `publicStatusWhere()`, `publicFeaturedWhere()` (status + `tags` contains
  `featured`), `publicSlugWhere(slug)` and the `isPublicStatus()` guard.
- `getProperties(options)` — listing query at `depth: 2`, limit 100. Handles
  purpose / category / locality / BHK / budget. Budget is applied to a
  purpose-specific price field (`pricing.price` for sale, `pricing.rentAmount`
  for rent, `pricing.monthlyLeasePayment` for lease), so a budget filter
  without a purpose is skipped rather than applied to the wrong column.
- `getPropertyLocalities(scope)` / `resolveLocalitySlug()` — filter options
  derived from live inventory, so the UI never offers an empty locality.
- `getFeaturedProperties({ limit })` — `publicFeaturedWhere()`, `-updatedAt`.
- `getPropertyBySlug(slug)` — wrapped in React `cache()` because the route uses
  it in both `generateMetadata` and the page body; returns `null` when the slug
  is not public.
- `getSimilarProperties()` — related inventory for the detail page.
- `mapProperty()` — the only place a CMS document becomes a `PublicProperty`.
  It converts Lexical rich text to HTML/plaintext, formats INR
  (`formatPrice.ts`), builds location display strings (`formatLocation.ts`),
  maps images through `toDeliveryImage()`, and refuses non-public documents.
- `filterParams.ts` — the URL query dialect: parse/serialize, budget bands,
  labels, and `legacyTypeToFilters()` for the old single `type` parameter.

### Projects — `lib/projects/`

Same shape. `PUBLIC_PROJECT_STATUSES` is `upcoming`, `under-construction`,
`ready-to-move`, `completed`, `sold-out` — everything except `draft`.
`getProjects({ projectType, status, isNew, limit })` at `depth: 2`,
`getProjectBySlug()`, `getRelatedProjects()`, `mapProject()`.
Nearby-connectivity category labels come from `lib/nearby-locations/`.

### Channel partners — `lib/channel-partners/`

Deliberately the smallest version of the same pattern, with no `publicScope.ts`
because visibility is a single boolean:

- `getChannelPartners()` — `where: { active: { equals: true } }`, `depth: 1`
  (enough to populate the `logo` upload), limit 50,
  `sort: ['displayOrder', 'name']`.
- `mapChannelPartner()` — drops records with no name or an unpopulated logo,
  builds alt text from the partner name, re-validates that `websiteUrl` is
  http(s) before it can reach an `href`, and routes the logo through
  `toDeliveryImage()` unless it is an SVG.
